## 1. 총평

### 1.1 잘된 점 (유지)

- **인가 원칙이 정확하다.** "로그인 ≠ 권한", 클라이언트가 보낸 `user_id`·`approved_by` 불신, 서비스 키 우회 금지, RLS를 끄지 않기, 승인 후 불변(§10.3, §11.2)은 실무에서 자주 깨지는 지점을 정확히 짚었다.
- **정직한 표현 원칙.** "보냈다고 기록했어요", E2EE가 아니면 "운영자도 못 본다"고 쓰지 않기, 서버 확인 전 성공 표시 금지(§4.7, §5.3)는 보안 UX로도 옳다.
- **수집 최소화가 기본값이다.** 성별·혼인·소득을 받지 않는 설계(§7.1)는 포용성과 보안이 같은 방향을 향한 좋은 예다.
- **금액 계산**(정수 단위, 나머지 규칙, 과거 정산 스냅샷, 멱등 키, §11.3)이 잘 정리돼 있다.
- **보안 테스트 시나리오**(§12.1)가 구체적이고 "정상 요청이 성공하는지"까지 본다.

### 1.2 구조적 문제

1. **공격자를 잘못 고르고 있다.** 원문의 방어는 대부분 "다른 공간의 사용자"와 "외부 침입자"를 막는 데 맞춰져 있다. 하지만 커플 앱에서 가장 현실적인 위협은 **이미 정당한 권한을 가진 파트너**다. 그 사람은 상대의 잠금 해제된 휴대폰을 집을 수 있고, 이메일 비밀번호를 알 수 있으며, "동의해"라고 압박할 수 있다. RLS는 이 사람을 막지 못한다. 이 부분은 제품 설계로 막아야 한다.
2. **"두 사람 동의"가 언제나 안전장치인 것은 아니다.** 두 사람 동의는 변경을 막는 데는 유용하지만, **빠져나가는 것까지 막으면 통제 도구가 된다.**
3. **기록이 많을수록 감시 자료가 된다.** 지출 시각·내용, 집안일 완료 시각, 승인 시각, 감사 로그를 모으면 상대의 하루 동선이 나온다. 원문은 "기여 순위를 만들지 않는다"는 데서 멈췄고, 원자료 자체의 노출은 다루지 않았다.
4. **법 규정이 빠져 있다.** 한국 서비스인데 개인정보보호법·안전성 확보조치 기준이 없다. 출시 직전에 발견하면 데이터 모델을 다시 짜야 한다.
5. **MVP가 크다.** 합의 버전 관리, 정산, 반복 집안일, 캘린더, 초대, 연결 해제를 한 번에 하면 보안 검증이 얕아진다(§6 참고).

## 2. 보안 비판과 개정안

각 항목은 **원문 → 문제 → 개정안** 순서다.

### S-1. 파트너를 1순위 위협으로 (§10.1 개정)

**원문:** 위협 표에서 "현재 파트너: 개인 정보 열람·상대 승인 위조·계정 지배 방지"를 여러 주체 중 하나로 다룬다.

**문제:** 친밀한 관계 내 기술 악용(intimate partner surveillance) 연구에서 반복해서 확인되는 공격은 고급 해킹이 아니다. **물리적 접근, 비밀번호를 알고 있음, 강요**다. 공격자는 계정 주인을 연기할 수 있고, 피해자는 앱 사용을 강요당할 수도 있다.

**개정안: 위협 모델 v1.1**

| 주체·상황 | 할 수 있는 일 | 보호할 것 | 핵심 대응 |
|---|---|---|---|
| **A. 정당한 파트너(통제 성향)** | 공동 데이터 정상 열람, 반복 확인, 압박 | 상대의 동선·시간·소비 패턴, 빠져나갈 자유 | 감시용 신호 금지(S-3), 혼자 할 수 있는 철회(S-2), 혼자 할 수 있는 연결 해제 |
| **B. 상대 기기를 손에 든 파트너** | 잠금 해제된 상대 휴대폰에서 승인·내보내기·설정 변경 | 승인의 진정성, 계정 통제권 | 민감 작업 단계 인증(S-4), 세션 목록·원격 로그아웃 |
| **C. 상대 이메일/전화에 접근 가능한 파트너** | 비밀번호 재설정, 매직링크 가로채기 | 계정 소유권 | 패스키 우선, 이메일 변경 지연 적용(S-5) |
| **D. 연결 해제된 전 파트너** | 남은 세션, 캐시, 재초대, 괴롭힘 | 이후 활동, 새 공간 | 소속을 매 요청 DB에서 확인(S-7), 재초대 차단(S-9) |
| E. 다른 공간의 로그인 사용자 | ID 위조, 직접 API 호출 | 공간 격리 | RLS + 테스트(원문 유지) |
| F. 비로그인 사용자 | 열거, 초대 토큰 추측 | 계정·초대 존재 여부 | 일정한 응답, 요청 제한(원문 유지) |
| G. 운영자·서버 침해 | DB 열람 | 본문 | 수집 최소화, 운영자 접근 기록, 민감 주제 미저장(S-6) |
| H. 공급망·프레임워크 취약점 | 서버 코드 실행 | 전체 | 패치 주기, 의존성 고정(S-12) |

**제품 원칙 추가:** "앱의 어떤 기능도 한 사람이 다른 사람의 행동을 실시간으로 확인하거나, 상대가 앱을 떠나지 못하게 만드는 데 쓰일 수 없어야 한다."

### S-2. 동의 철회는 혼자서 (§3.1, §11.2 개정) — 치명

**원문:** "50:50 변경안을 제안하더라도 두 사람이 새 버전에 동의하기 전에는 기존 규칙이 유지된다."

**문제:** 생활비라면 합리적이다. 하지만 같은 장치가 #27(귀가 연락), #28(휴대폰·비밀번호), #31(가족 방문)에도 적용된다. A가 "매일 밤 10시까지 위치 공유하기"를 약속하게 한 뒤 변경 제안을 무시하면, 앱 안에서 그 약속은 계속 "적용 중"으로 남는다. **앱이 통제를 공식 문서처럼 만들어 준다.**

**개정안:**

- 약속 상태에 **`철회됨(withdrawn)`** 을 추가한다. 어느 구성원이든 혼자서, 이유 없이, 즉시 철회할 수 있다.
- 상태 흐름: `개인 초안 → 제안됨 → 두 사람 동의 → 적용 대기/적용 중 → (대체됨 | 종료 | 철회됨)`
- **변경은 둘이, 철회는 혼자서.** 철회는 이전 버전으로 되돌리는 것이 아니라 "현재 합의 없음" 상태가 된다.
- 금전 약속이 철회되면: 철회 시각 이후 새 지출은 기본 분담이 비어 있고, 입력할 때마다 분담을 직접 정한다. 이미 확정된 정산은 바뀌지 않는다. 철회 전 미확정 지출은 철회 전 규칙을 따른다(스냅샷).
- 철회 알림은 중립적으로 쓴다: "생활비 약속이 철회됐어요. 다시 이야기해볼까요?" 누가 철회했는지는 상세 화면에서만 표시한다.
- 개인 경계에 관한 템플릿(#27, #28)은 **특정 행동을 의무화하는 문장 대신 서로의 경계를 적는 형식**으로 만든다. 예: "연락 기대" 템플릿은 "늦어질 때 알려주면 좋겠어요"까지만, "N분마다 연락" 같은 주기 필드는 없다.

### S-3. 감시 신호 금지 (§4, §7.3에 추가)

**문제:** 원문은 순위·점수를 금지했지만 더 직접적인 감시 신호는 다루지 않았다.

**개정안 — 만들지 않을 기능(명시적 금지 목록):**

- 읽음 표시. 제안 수신 화면에서 "나중에 보기"를 눌렀는지 상대가 알 수 없어야 한다. 상대에게 보이는 상태는 "답변 전" 하나뿐이다.
- 마지막 접속 시각, 온라인 표시, "입력 중".
- Supabase Realtime **Presence** 사용 금지(접속 여부가 그대로 노출된다).
- 집안일 완료 **시각** 노출. 파트너에게는 날짜만 보여준다. 정밀 시각은 서버에서 정렬·중복 방지에만 쓰고, 파트너 응답에는 담지 않는다.
- 지출의 위치·가맹점 자동 수집(영수증 인식 도입 시에도 가맹점 주소 저장 금지).
- "상대가 이 화면을 봤어요" 류의 알림, 응답 독촉 자동 반복 알림(원문의 비난 금지를 확장).
- 감사 로그를 파트너에게 보여주는 기능. 감사 로그는 운영 보안용이고 사용자 간 증거 자료가 아니다.

**구현 규칙:** 파트너에게 반환되는 API 응답 스키마를 별도로 정의한다(`PartnerView`). 테스트로 `last_seen`, `viewed_at`, `completed_at`(시각 포함) 같은 필드가 파트너 응답에 **없다**는 것을 확인한다(→ SEC-17).

### S-4. 승인의 진정성: 단계 인증과 내용 고정 (§10.2, §11.2 개정)

**원문:** "상대 승인 위조 방지", "승인자는 검증된 세션에서 정한다."

**문제:** 서버 세션 검증은 "그 계정에서 눌렀다"는 것만 증명한다. 같은 집에서 상대의 잠금 해제된 휴대폰으로 누르는 것은 막지 못한다(위협 B). 또 화면을 연 뒤 내용이 바뀌었는데 예전 화면에서 동의 버튼을 누르는 TOCTOU 문제도 있다.

**개정안:**

1. **동의는 내용 해시에 묶는다.** 동의 요청에 `version_id`와 화면이 받은 `content_hash`(정규화한 본문의 SHA-256)를 함께 보내고, 서버는 현재 버전의 해시와 다르면 거부한다. 동의 행에도 해시를 저장한다.
2. **단계 인증(step-up) 대상 작업**: 금전 약속 동의, 정산 확정, 내보내기, 이메일·로그인 수단 변경, 세션 전체 로그아웃. 패스키/생체 인증이 있으면 한 번의 터치로 끝나므로 마찰이 작다. 최근 인증 후 5분 안이면 생략.
3. 연결 해제는 **단계 인증 없이도** 가능하게 한다(빠져나가는 길에 장애물을 두지 않는다). 대신 되돌리기 어렵다는 확인 화면만 둔다.
4. **세션·기기 목록**: 기기 종류, 대략의 시작 시각만 표시한다(정밀 위치·IP 표시는 오히려 공격자에게 정보가 된다). 개별·전체 로그아웃 지원.
5. 정직한 고지: "앱의 동의 기록은 그 순간 그 계정에서 동의 버튼이 눌렸다는 기록이에요. 현재의 동의를 대신하지 않아요." (원문 §2 민감 주제 문장을 모든 약속으로 확장)

### S-5. 계정 탈취·복구 (§10.2 개정)

**문제:** 매직링크·이메일 재설정은 **이메일함을 가진 사람이 계정 주인**이라는 뜻이다. 파트너끼리 이메일 비밀번호를 알거나 같은 기기에 이메일이 로그인된 경우가 흔하다.

**개정안:**

- 로그인 수단 우선순위: **패스키 → 이메일+비밀번호(유출 비밀번호 차단) + TOTP** → 이메일 매직링크(보조).
- 가입 직후 패스키 등록을 권장한다(강요하지 않음).
- **이메일 변경**: 단계 인증 + 기존 이메일과 새 이메일 양쪽 확인 + 기존 이메일로 취소 링크 발송.
- **복구로 들어온 세션**: 다른 모든 세션을 끊고, 이후 24시간 동안 내보내기·연결 해제 취소 같은 고위험 작업을 막는 쿨다운을 검토한다(→ 결정 D-4).
- 복구 코드 1회용 10개 발급, 서버에는 해시만 저장.
- 로그인 실패 메시지는 계정 존재 여부를 드러내지 않는다.
- **새 기기 로그인 알림의 함정:** 알림을 보내면 공격자가 같은 이메일함을 보고 있을 수 있다. 앱 안의 세션 목록을 기본으로 두고, 이메일 알림은 본인이 켜는 선택 사항으로 둔다.

### S-6. 민감 주제와 E2EE 결정 (§2 민감 주제, §10.5 개정)

**문제 1 — 모순:** 원문은 성생활·피임 정보를 "필수 수집하지 않는다"고 하면서도 해당 주제를 약속으로 쓸 수 있게 열어 둔다. 자유 작성 본문에 그 내용이 들어가면 서버에 **개인정보보호법 제23조 민감정보(건강, 성생활 등)** 가 저장된다. 그러면 별도 동의와 더 강한 안전조치가 필요하다.

**개정안:**

- #29(성생활·스킨십), #38(자녀 계획·피임), #40 중 건강 상세는 **대화 안내 카드**로만 제공한다. 질문 목록을 읽고 둘이 대화하는 용도이며, 답변 입력란이나 저장 기능이 없다. 카드를 열었다는 기록도 남기지 않는다(분석 이벤트 포함).
- 자유 작성 약속 본문에는 "건강·성생활 같은 민감한 내용은 적지 않는 것을 권해요" 안내를 둔다. 필터로 막지는 않는다(오탐이 많고 내용 검사 자체가 감시다).

**문제 2 — E2EE 미정:** 원문 §13은 E2EE 필수 여부를 구현 전 결정 사항으로 남겼다.

**결정 권고: MVP는 E2EE를 하지 않는다.** 근거:

1. 1순위 공격자(파트너)는 **단말 쪽**에 있다. 두 사람이 공유하는 데이터는 E2EE를 해도 파트너가 복호화할 수 있다.
2. 두 사람 공유 키, 다중 기기, 복구, 연결 해제 후 키 교체, 서버 측 정산 계산, 알림이 모두 복잡해지고 키 분실 시 데이터를 잃는다. 검증되지 않은 E2EE는 없는 것보다 위험하다(잘못된 안심).
3. 운영자 위협은 **민감 본문을 저장하지 않는 방식**(위의 대화 카드 정책)과 운영자 접근 기록으로 대부분 줄일 수 있다.

→ 문서·UI에서 "암호화되어 안전해요" 같은 모호한 문구를 쓰지 않는다. 쓸 수 있는 문구: "전송과 저장 중에 암호화돼요. 서비스 운영자는 엄격히 제한된 경우에만 접근할 수 있고, 접근은 기록돼요."

### S-7. Supabase·PostgreSQL 함정 (§10.3 구체화)

원문은 원칙이 옳지만, Supabase에서 실제로 사고가 나는 지점이 빠져 있다. 아래는 **필수 구현 규칙**이다.

| # | 함정 | 규칙 |
|---|---|---|
| 7-1 | `auth.jwt() -> 'user_metadata'`는 **사용자가 직접 수정 가능**하다 | RLS·권한 판단에 `user_metadata`/`raw_user_meta_data`를 쓰지 않는다 |
| 7-2 | 소속 공간을 JWT 커스텀 클레임에 넣으면 연결 해제 후에도 **토큰 만료 전까지 유효** | 소속은 **매 요청 `memberships` 테이블에서** 확인한다. JWT 클레임에 `household_id`를 넣지 않는다 |
| 7-3 | RLS는 **행** 단위다. 행을 읽을 수 있으면 PostgREST로 모든 열을 `select`할 수 있다 | 파트너가 볼 정보와 본인만 볼 정보는 **테이블을 나눈다**(`profiles_shared` / `profiles_private`). 또는 열 단위 GRANT |
| 7-4 | 뷰는 기본적으로 **소유자 권한**으로 실행되어 RLS를 우회한다 | 모든 뷰는 `with (security_invoker = true)` |
| 7-5 | 노출 스키마의 함수는 기본적으로 **PUBLIC 실행 권한**이 있어 RPC로 호출 가능 | 함수 생성 직후 `revoke execute ... from public, anon`. 헬퍼 함수는 비노출 스키마(`app`)에 둔다 |
| 7-6 | `security definer` 함수의 `search_path` 탈취 | `set search_path = ''`로 고정하고 모든 객체를 스키마까지 적는다 |
| 7-7 | UPDATE 정책에 `WITH CHECK`가 없으면 `household_id`를 다른 값으로 옮길 수 있다 | 모든 UPDATE 정책에 `USING`과 `WITH CHECK`를 둘 다 둔다. 소속·작성자 열은 **열 단위 UPDATE 권한에서 제외**한다 |
| 7-8 | `anon` 역할에 테이블 권한이 남아 있음 | `revoke all on all tables in schema public from anon`. 비로그인 경로는 초대 확인 RPC 하나뿐 |
| 7-9 | Realtime Broadcast/Presence 채널은 테이블 RLS와 **별도**의 인가가 필요 | MVP는 `postgres_changes`만 사용(RLS 적용). Broadcast를 쓰면 Realtime Authorization 정책을 둔다. Presence는 금지(S-3) |
| 7-10 | 익명 로그인(anonymous sign-in)이 켜져 있으면 누구나 `authenticated` 역할을 얻는다 | 익명 로그인 끈다. "가상 데이터 둘러보기"(§4.2)는 **서버 없이 클라이언트 고정 데이터**로 만든다 |
| 7-11 | 승인 후 불변을 RLS만으로 지키기 어렵다 | 트리거로 강제한다(아래 예시) |
| 7-12 | 백업/PITR에 삭제된 데이터가 남는다 | 보존 기간을 개인정보 처리방침에 적고, 복원 후 삭제 요청 재적용 절차를 둔다 |

**예시 — 소속 확인 헬퍼와 지출 정책** (구현 참고용 초안, 검증 전)

```sql
create schema if not exists app;  -- PostgREST에 노출하지 않는 스키마

create or replace function app.is_active_member(hid uuid)
returns boolean
language sql stable security definer
set search_path = ''
as $$
  select exists (
    select 1
    from public.memberships m
    join public.households h on h.id = m.household_id
    where m.household_id = hid
      and m.user_id = (select auth.uid())
      and m.status = 'active'
      and h.status = 'active'
  );
$$;
revoke all on function app.is_active_member(uuid) from public, anon;
grant usage on schema app to authenticated;
grant execute on function app.is_active_member(uuid) to authenticated;

alter table public.expenses enable row level security;
alter table public.expenses force row level security;

create policy expenses_select on public.expenses
  for select to authenticated
  using (app.is_active_member(household_id));

create policy expenses_insert on public.expenses
  for insert to authenticated
  with check (
    app.is_active_member(household_id)
    and created_by = (select auth.uid())
  );

-- 작성자만, 정산 확정 전까지만 수정
create policy expenses_update on public.expenses
  for update to authenticated
  using  (created_by = (select auth.uid()) and settlement_id is null and app.is_active_member(household_id))
  with check (created_by = (select auth.uid()) and settlement_id is null and app.is_active_member(household_id));

-- 소속·작성자·정산 연결 열은 클라이언트가 바꿀 수 없게
revoke update on public.expenses from authenticated;
grant update (amount, currency, description, paid_by, split_snapshot, spent_on, version)
  on public.expenses to authenticated;
```

**예시 — 동의는 RPC로만, 내용 해시에 묶기**

```sql
-- approvals 테이블에 직접 INSERT 권한을 주지 않는다
revoke insert, update, delete on public.approvals from authenticated;

create or replace function public.approve_agreement_version(p_version_id uuid, p_content_hash text)
returns void
language plpgsql security definer
set search_path = ''
as $$
declare
  v public.agreement_versions;
  approved_count int;
begin
  select * into v from public.agreement_versions
   where id = p_version_id
   for update;                                   -- 동시 승인 직렬화

  if not found or not app.is_active_member(v.household_id) then
    raise exception 'not_found' using errcode = 'P0002';  -- 존재 여부를 드러내지 않음
  end if;
  if v.status <> 'proposed' then
    raise exception 'invalid_state';
  end if;
  if v.content_hash <> p_content_hash then
    raise exception 'stale_content';             -- 화면을 연 뒤 내용이 바뀜
  end if;

  insert into public.approvals (version_id, user_id, content_hash)
  values (v.id, (select auth.uid()), p_content_hash)
  on conflict (version_id, user_id) do nothing;

  select count(*) into approved_count
    from public.approvals a
    join public.memberships m
      on m.user_id = a.user_id and m.household_id = v.household_id and m.status = 'active'
   where a.version_id = v.id;

  if approved_count = 2 then
    update public.agreement_versions
       set status = case when v.effective_from > current_date then 'scheduled' else 'active' end
     where id = v.id;
  end if;
end;
$$;
revoke all on function public.approve_agreement_version(uuid, text) from public, anon;
grant execute on function public.approve_agreement_version(uuid, text) to authenticated;
-- 단계 인증 여부는 서버(Next.js)에서 확인한 뒤에만 이 RPC를 호출한다(S-4).
-- DB에서도 확인하려면 auth.jwt()의 aal/amr 클레임 검사를 추가한다.

-- 승인 이후 본문 불변
create or replace function app.forbid_content_change()
returns trigger language plpgsql set search_path = '' as $$
begin
  if old.status <> 'draft' and (new.content is distinct from old.content
                                or new.content_hash is distinct from old.content_hash
                                or new.household_id is distinct from old.household_id) then
    raise exception 'immutable_version';
  end if;
  return new;
end;
$$;
create trigger agreement_versions_immutable
  before update on public.agreement_versions
  for each row execute function app.forbid_content_change();
```

### S-8. Next.js 함정 (§9, §10.3 구체화)

| # | 함정 | 규칙 |
|---|---|---|
| 8-1 | Server Action은 화면에 버튼이 없어도 **누구나 호출 가능한 공개 POST 엔드포인트**다 | 모든 Server Action/Route Handler 첫 줄에서 세션 확인 + 대상 권한 확인. 공통 래퍼(`withAuthz`)로 강제하고 린트 규칙으로 래퍼 누락을 잡는다 |
| 8-2 | 미들웨어 검사 우회 취약점 이력(2025년 `x-middleware-subrequest` 헤더 우회, CVE-2025-29927) | 미들웨어는 리다이렉트용 편의 기능일 뿐 권한 경계가 아니다(원문 방향을 구체적 근거로 강화) |
| 8-3 | 사용자별 데이터가 `fetch` 캐시, `unstable_cache`, `"use cache"`, 정적 렌더링으로 **다른 사용자에게 재사용** | 인증된 경로는 동적 렌더링으로 고정, 사용자 데이터에 공유 캐시 함수 금지, 응답 헤더 `Cache-Control: private, no-store`. SEC-10을 실제 두 계정으로 자동화 |
| 8-4 | RSC 페이로드로 서버 객체 전체가 클라이언트에 직렬화 | 서버에서 DTO로 필요한 필드만 골라 넘긴다(`PartnerView`, S-3). `server-only` 패키지로 서버 모듈의 클라이언트 import 차단 |
| 8-5 | 프레임워크 자체의 심각한 취약점(예: 2025년 12월 RSC 원격 코드 실행 취약점 CVE-2025-55182) | 보안 공지 구독, 심각도 높음 이상은 **72시간 내 패치** 목표를 운영 규칙으로 둔다 |
| 8-6 | `NEXT_PUBLIC_` 접두어 환경변수는 번들에 들어간다 | 서비스 키 변수명에 `NEXT_PUBLIC_` 금지를 CI에서 검사(SEC-12 강화) |
| 8-7 | Supabase SSR 쿠키는 기본적으로 JS가 읽을 수 있다 | 원문 §10.2의 지적을 결정으로 바꾼다: **브라우저 SDK로 DB에 직접 붙지 않고, 모든 데이터 요청을 서버(Server Action/Route Handler)를 통해** 보낸다. 그러면 쿠키를 HttpOnly로 둘 수 있고 XSS 시 토큰 탈취 범위가 줄어든다. RLS는 서버에서도 사용자 JWT로 그대로 적용된다 |

### S-9. 초대: 링크 + 양쪽 확인 코드 (§10.4 개정)

**문제:** 한국에서는 초대 링크를 메신저로 보내는 경우가 대부분이다. 링크가 단체방에 잘못 가거나 미리보기 봇·다른 사람이 먼저 열면, "로그인 + 명시적 수락"만으로는 **엉뚱한 사람이 공간에 들어올 수 있다.** 원문의 "검증된 수신 대상 확인"은 이메일 지정 초대에만 통한다.

**개정안 — 페어링 방식:**

1. 초대자가 링크 생성(32바이트 이상 무작위, 서버엔 해시, 유효 24시간, 1회용).
2. 수신자가 링크를 열고 로그인 → "수락 요청" 상태가 된다. **아직 공간에 들어가지 않는다.**
3. **양쪽 화면에 같은 6자리 확인 코드**가 보인다(초대 ID와 수신자 ID로 서버가 생성).
4. 초대자가 자기 화면에서 "OO 님이 맞아요(코드 확인)"를 눌러야 멤버십이 생긴다. 대면이나 전화로 코드를 맞춰보도록 안내한다.
5. 초대자가 확인하기 전에는 수신자에게 초대자 이름·공간 정보가 보이지 않는다(링크만으로 정보 유출 없음).

**추가 규칙:**

- 초대 링크 경로에 토큰을 두되, 첫 요청에서 서버가 HttpOnly 쿠키로 옮기고 **토큰 없는 URL로 리다이렉트**한다(Referer·브라우저 기록 유출 감소). `Referrer-Policy: no-referrer`.
- 링크 미리보기(OG)는 고정 문구 "초대 링크예요"만. 메신저 미리보기 봇의 GET이 초대를 소모하지 않게, **GET은 아무 상태도 바꾸지 않는다.**
- 한 사람이 동시에 속할 수 있는 활성 공간은 1개. 정원(2명)은 DB 제약으로 강제(원문 SEC-07 유지).
- **재초대 차단:** 연결을 해제한 사람은 상대에게서 오는 초대를 차단할 수 있다(사용자 ID 단위). 초대 생성은 사용자당 하루 N회로 제한.

### S-10. 연결 해제와 공동 기록 (§10.4, §11 개정)

**문제:** 원문은 보존·내보내기·삭제를 "별도 정책"으로 미뤘다. 이 결정은 데이터 모델(누가 어떤 행의 소유자인가)을 바꾸므로 미룰 수 없다.

**개정안 — 기본 정책(결정 D-2에서 확정):**

| 시점 | 해제한 사람 | 상대 |
|---|---|---|
| 해제 즉시 | 새 데이터 생성 불가. 종료 시점 스냅샷 읽기 전용 열람·내보내기 | 같음. 해제 사실은 중립 알림으로 받음("함께 쓰던 공간이 종료됐어요") |
| 30일 동안 | 읽기 전용 열람·내보내기 | 같음 |
| 30일 후 | 공동 기록 삭제 | 같음 |
| 언제든 | 자기 계정 삭제 가능. 상대의 스냅샷에서 내 표시 이름은 "이전 구성원"으로 바뀜 | — |

- **안전 옵션:** 해제할 때 "상대의 열람도 즉시 끝내기"를 선택할 수 있게 할지 → 상대도 정산 기록이 필요하므로 충돌한다. 권고: 금액·날짜·분담만 남긴 **정산 요약**은 상대에게 남기고, 자유 작성 본문(약속 메모, 지출 설명)은 즉시 끝내는 옵션을 둔다.
- 해제 처리는 하나의 트랜잭션 RPC로: 멤버십 종료 → 공간 상태 `ended` → 미사용 초대 취소 → 예약 작업 취소. RLS가 소속을 매 요청 확인하므로(S-7 7-2) 기존 세션은 다음 요청부터 막힌다. 클라이언트는 다음 응답의 `access_revoked`를 받으면 메모리 캐시를 비운다.
- 해제 화면 하단에 **도움 받을 수 있는 곳**(여성긴급전화 1366 등 공공 상담 창구)을 조용히 안내한다. 관계를 판단하는 문구는 쓰지 않는다.

### S-12. 운영·공급망 보강 (§10.7 보강)

- 패키지 매니저 잠금 파일 + 설치 스크립트 실행 제한(`ignore-scripts` 기본, 필요한 패키지만 허용 목록).
- 새로 공개된 지 7일 미만인 패키지 버전 설치를 늦추는 정책(최근 npm 공급망 공격 대응).
- GitHub: 기본 브랜치 보호, 서명 커밋 권장, Dependabot/비밀정보 스캔, Actions는 커밋 SHA로 고정하고 `permissions: read-all` 기본.
- 에러 추적 SDK는 **기본 수집을 끄고 허용 목록으로** 켠다(요청 본문·쿠키·로컬 변수 수집 금지).
- 분석 도구: MVP에서 제3자 분석 스크립트 넣지 않음. 필요하면 자체 집계(화면 단위 카운트만, 사용자 식별자 없음).
- CSP: nonce 기반 `script-src`, `frame-ancestors 'none'`, `object-src 'none'`, `base-uri 'none'`. Trusted Types는 가능하면 적용.

## 5. 소득 비례 계산의 정직한 설계 (§3.3 개정)

**원문:** "소득은 계산 중 기기 메모리에서만 처리하고 … 비율로 소득 관계가 추정될 수 있다는 점은 필요한 맥락에서 안내한다."

**문제:** "추정"이 아니라 **역산**이다. 비율 60:40이 공유되면, 자기 소득이 300만 원인 사람은 상대 소득이 200만 원임을 즉시 안다. 또 두 소득을 한 기기에 입력하는 사람은 이미 둘 다 안다. "기기에서만 처리"는 **서버와 운영자에 대한 보호**일 뿐, 파트너에 대한 보호가 아니다.

**개정안:**

- 계산기 안내 문구: "나눌 비율을 보면 서로의 소득 차이를 짐작할 수 있어요. 소득은 저장하지 않아요." (짧게, 계산 전에)
- 비율은 **5% 단위로 반올림**해서 저장·공유한다(예: 58.3% → 60%). 반올림 전 정밀 비율은 저장하지 않는다.
- "소득에 맞춰 나누기"는 계산을 돕는 도구일 뿐, 결과는 늘 "비율 정하기"로 저장된다. 즉 **약속에는 어떤 방식으로 계산했는지 남기지 않는다.** (계산 방식이 남으면 소득 정보가 있었다는 메타정보가 된다)
- 소득 입력란은 `autocomplete="off"`, 화면 이탈 시 값 초기화, 분석 이벤트·에러 로그에서 이 화면 입력값을 수집하지 않는다(원문 유지).

## 6. 제품·UX 비판과 디벨롭

### 6.1 MVP 범위 축소

원문 MVP는 약속·생활비·정산·집안일·캘린더·초대·연결 해제를 모두 포함한다. 보안 검증을 깊게 하려면 표면을 줄여야 한다.

| 단계 | 포함 | 이유 |
|---|---|---|
| **MVP-0 (기반)** | 인증(패스키), 공간, 페어링 초대, 연결 해제, RLS, 권한 테스트 | 모든 기능의 보안 기반. 화면은 최소 |
| **MVP-1** | 약속(버전·동의·철회), 지출 기록, 월 정산 | 앱의 핵심 가치. 금전 정확성 검증에 집중 |
| **MVP-2** | 집안일(반복·완료 기준·교환 요청) | 반복 생성·시간대 문제가 크므로 분리 |
| 다음 | 캘린더 | MVP-2까지의 날짜 데이터(납부일, 재검토일, 집안일)를 모아 보여주는 **파생 화면**으로 시작. 자체 일정 입력은 그 다음 |

→ 하단 탭은 MVP-1에서 **홈 / 생활비 / 약속** 세 개로 시작하고, 일정 탭은 캘린더 단계에서 추가한다.

### 6.2 "제안자의 동의" 미결 사항 확정

원문 §11.2는 "제안자가 전송할 때 자신의 동의를 함께 기록할지 UI에 명시한다"며 결정을 미뤘다. **결정: 제안 보내기 = 제안자의 동의.** 버튼 문구를 "이 내용으로 제안하기(나는 동의해요)"로 한다. 상대가 수정 제안을 보내면 그 수정안에는 수정 제안자의 동의만 기록되고 원 제안자는 다시 동의해야 한다(원문 규칙과 일치).

### 6.3 지출 기록의 신뢰 문제

원문은 일상 기록에 매번 승인을 요구하지 않는다(좋음). 하지만 그러면 한쪽이 상대 이름으로 "상대가 결제함" 지출을 올리거나 금액을 부풀릴 수 있다. 개정: 작성자만 수정 가능, 상대는 **"확인 필요"** 표시만 가능, 확인 필요 지출은 정산 확정 전 화면 상단에 모아서 보여준다. 정산은 두 사람 모두 확정해야 완료된다.

### 6.4 같은 표시 이름 문제

원문은 동일한 표시 이름을 허용한다(§7.1). 두 명뿐인 공간에서 둘 다 "민"이면 "민 님의 확인을 기다려요"가 누구인지 모호해지고, 악의적으로 상대 이름을 따라 해 혼동을 줄 수 있다. 개정: 공간 안에서는 늘 **"나" / 상대 표시 이름**으로 쓰고, 상대와 같은 이름이면 상대 쪽에 색·이니셜을 강제로 다르게 표시한다.

### 6.5 문서 자체에 대한 의견

- §5(토스 조사), §6(디자인 스킬 조사)은 참고 자료로 가치가 있지만 구현 명세의 핵심은 아니다. 다음 버전에서 부록으로 옮기고 본문은 요구사항 위주로 줄이길 권한다.
- §2의 42개 항목은 **콘텐츠 지도**로 매우 좋다. 다만 각 항목에 "MVP 템플릿 여부 / 대화 카드 여부 / 미지원" 열을 추가하면 개발 범위가 명확해진다. 예: 01·02·03·04 → MVP 템플릿, 29·38 → 대화 카드 전용, 07(부채 공유) → 대화 카드(금액 저장 안 함).
- §1.1의 근거 인용은 한계까지 밝혀서 좋다. 유지.

| SEC-17 | 파트너 응답에서 감시 신호 검사 | `last_seen`, `viewed_at`, 시각 포함 `completed_at`, 이메일 필드 없음 |
| SEC-18 | `user_metadata`에 다른 `household_id`를 넣고 요청 | 접근 불가 |
| SEC-19 | 연결 해제 직후, 만료 전 JWT로 PostgREST 직접 호출 | 공동 데이터 조회·생성 실패 |
| SEC-20 | 초대 링크를 제3자가 먼저 열고 로그인·수락 요청 | 초대자 코드 확인 전 멤버십 없음, 초대자 정보 미노출 |
| SEC-21 | 메신저 미리보기 봇처럼 초대 링크 GET 반복 | 초대 상태 변화 없음, 응답에 이름·관계 없음 |
| SEC-22 | 노출 스키마 함수 목록을 `anon`으로 RPC 호출 | 초대 확인 RPC 외 전부 거부 |
| SEC-23 | 뷰를 통한 다른 공간 데이터 조회 | `security_invoker`로 RLS 적용, 0행 |
| SEC-24 | `expenses.household_id`·`created_by` 열 UPDATE 시도 | 권한 오류 |
| SEC-25 | 단계 인증 없이 금전 약속 동의·정산 확정·내보내기 | 거부 |
| SEC-26 | 이메일 변경 요청 직후 기존 이메일 취소 링크 | 변경 취소, 새 세션 회수 |
| SEC-27 | 민감 주제 대화 카드 열기 | 서버 요청·분석 이벤트 없음 |
| SEC-28 | 해제한 사용자에게 상대가 재초대 | 차단 설정 시 초대 생성 실패, 차단 사실은 상대에게 미노출 |

## 11. 운영·수익 계획 (재판 반영, 신규)

**배경:** `/court` 모의 재판(배심원 6명, 유죄 5:1)에서 쟁점이 된 것은 프로토타입이 아니라 계획서의 빈칸이었다. 배심원 6명이 모두 지적한 것은 광고와 개인정보 원칙의 충돌이었고, 3명씩은 운영비를 누가 내는지와 월 고정비 숫자를 요구했다. 이 절은 그 세 가지를 채운다.

**전제:** 이 앱은 토이 프로젝트다. 수입은 **0원으로 가정**하고 계획한다. 광고·후원은 생기면 운영비를 보태는 수단일 뿐, 서비스가 유지되는 조건이 아니다.

### 11.1 광고 원칙 (D-9)

가장 중요한 위협은 파트너에 의한 통제·감시다(S-1). 그런데 광고가 사용자를 추적하면 같은 정보가 제3자에게 흘러간다. 그래서 **추적이 구조적으로 불가능한 형태만** 허용한다.

| 항목 | 규칙 |
|---|---|
| 형식 | 운영자가 광고주와 **직접 계약한 정적 배너**(이미지 + 짧은 문구) 1개 |
| 기술 | 이미지는 우리 도메인에서 내보낸다. **외부 스크립트·iframe·추적 픽셀·쿠키 없음.** 현재 CSP(`script-src`는 nonce, `img-src 'self'`)를 바꾸지 않고 넣을 수 있어야 한다 |
| 링크 | 사용자 식별자가 없는 고정 URL로 연결하는 일반 링크(`rel="sponsored noopener noreferrer"`). `Referrer-Policy: no-referrer`는 이미 적용돼 있다 |
| 타기팅 | **없음.** 모든 사용자에게 같은 광고를 보여준다. 사용자 데이터(지출 내용·약속·집안일·지역)로 광고를 고르지 않는다 |
| 집계 | 광고별 **하루 노출·클릭 총합**만 서버에서 센다. 사용자 ID·IP·세션은 기록하지 않는다. 광고주에게는 이 총합만 준다 |
| 표시 | 배너에 "광고" 라벨을 붙인다 |
| 광고주가 없을 때 | 광고 자리를 아예 그리지 않는다(빈 자리 없음) |

**광고를 둘 수 있는 화면:** 로그인·둘러보기 화면, 설정 화면 맨 아래.

**광고를 두지 않는 화면:** 홈(오늘 할 일·생활비 요약이 있음), 생활비, 약속, 집안일, 초대, 연결 해제·종료 화면, 대화 카드, 본인 확인 창. 관계·돈·갈등을 다루는 순간에 광고가 끼어들지 않게 한다.

**받지 않는 광고 업종:**
- 위치 추적·휴대폰 모니터링 앱, 흥신소·탐정. 이 앱이 막으려는 통제 도구 그 자체다.
- 대출·도박.
- 데이팅·결혼정보. 특정 관계 형태를 성공 경로로 가정한다(원문 §7.2).
- 건강·성 관련 제품. 민감 주제를 저장하지 않는다는 원칙(S-6)과 같은 이유다.

**금지:** 구글 애드센스 같은 광고 네트워크와 제3자 광고 SDK. 도입하려면 이 기획서를 다시 개정하고 별도 보안 검토를 거쳐야 한다.

### 11.2 후원 원칙 (D-10)

- 설정 화면에 **외부 후원 페이지 링크** 하나만 둔다. 앱 안에서는 결제하지 않고 결제 정보도 받지 않는다.
- 후원 여부를 앱 계정과 연결하지 않는다. 후원자 이름·금액을 앱에 저장하지 않는다.
- 후원해도 기능이나 광고 노출이 달라지지 않는다. 후원자만 광고를 숨기는 식의 차등을 두지 않는다. 그러려면 후원 여부를 계정에 기록해야 하기 때문이다.

### 11.3 월 고정비 추정

> 아래 가격은 2026년 10월 기준 각 서비스의 공개 요금제를 바탕으로 한 **추정치**다. 계약 전에 요금 페이지를 다시 확인한다. 환율은 1달러 = 1,400원으로 계산했다.

| 항목 | 단계 0: 지금 (가상 데이터, 비공개) | 단계 1: 공개 베타 (실제 데이터, 광고·후원 없음) | 단계 2: 광고·후원 시작 |
|---|---|---|---|
| 웹 호스팅 (Vercel) | 무료(Hobby) | 무료(Hobby) | **Pro 월 $20 ≈ 28,000원**. Hobby 요금제는 비상업적 개인 용도로 제한되므로, 광고를 붙이면 유료 전환이 필요하다 |
| DB·인증 (Supabase, 서울 리전) | 무료 | **Pro 월 $25 ≈ 35,000원**. 무료 요금제는 일정 기간 쓰지 않으면 일시 정지되고 자동 백업이 없다. 실제 커플의 기록을 맡기려면 백업이 필요하다 | 월 $25 ≈ 35,000원 |
| 도메인 | 없음 | 연 2~3만 원 (월 약 2,000원) | 같음 |
| 메일 발송 (인증·알림) | 없음 | 무료 구간 안에서 시작 | 같음 |
| 웹 푸시 | 없음 | 무료(표준 Web Push) | 같음 |
| 오류 추적 | 없음 | 무료 구간 (S-12 마스킹 설정 필수) | 같음 |
| **월 합계** | **0원** | **약 37,000원** | **약 65,000원** |
| **연 합계** | 0원 | 약 44만 원 | 약 78만 원 |

**1회성 비용**
- 개인정보 처리방침: 개인정보보호위원회의 처리방침 작성 지원 도구로 초안을 만든다. 변호사 검토 비용은 **견적을 받아 이 칸에 적는다.** 견적 전에는 금액을 미정으로 둔다.
- 외부 보안 점검: 선택 사항이다. 하게 되면 같은 방식으로 견적을 받아 적는다.

**수입이 운영비를 덮으려면:** 단계 2의 월 65,000원을 광고로 채우려면 월 6만 5천 원 이상의 직접 계약 광고주가 필요하다. 토이 프로젝트 초기에는 현실적으로 기대하기 어렵다. 그래서 수입을 0으로 놓고 §11.4의 부담 원칙을 둔다.

### 11.4 운영비 부담과 서비스 종료 (D-11)

> **운영자 확인 필요:** 아래 첫 문장은 운영자(프로젝트 소유자)의 약속이다. 기획서 작성자가 대신 정할 수 없다. 동의하면 체크하고, 다르면 고쳐 쓴다.

- [ ] 운영자는 광고·후원 수입과 무관하게 §11.3의 월 고정비를 직접 부담한다.
- 부담이 어려워지면 아래 **종료 절차**를 따른다. 갑자기 서비스를 끄지 않는다.
  1. 종료일 최소 **30일 전**에 앱 안에서 두 사람 모두에게 알린다. 알림 문구에 이름·관계 정보는 넣지 않는다(원문 §7.3).
  2. 종료일까지 각자 **내 기록 내려받기**(이미 구현됨)를 쓸 수 있게 한다.
  3. 종료일에 DB를 삭제한다. 백업은 보존 기간이 지나면 자동으로 지워지게 둔다(S-7 7-12). 삭제 완료를 처리방침에 정한 방식으로 공지한다.
- 이 절차는 개인정보 처리방침의 "파기" 항목에 그대로 적는다(S-11).

### 11.5 출시 관문 — 실제 커플의 데이터를 받기 전 (D-12)

재판의 판결 요지: "실제 인증과 DB를 붙이기 전에는 실제 커플의 데이터를 받지 말 것." 아래를 **모두** 만족해야 단계 1(공개 베타)로 간다.

- [ ] 실제 인증(패스키 우선) 연결, 가짜 로그인 제거
- [ ] 실제 DB 연결, `npm run test:db`의 RLS 테스트를 실제 Supabase 프로젝트에서도 통과
- [ ] 자동 백업 켜짐(Supabase Pro), 복원 리허설 1회
- [ ] 개인정보 처리방침·동의 화면 게시(국외 이전·파기·종료 절차 포함)
- [ ] 요청 제한(로그인·초대·내보내기)
- [ ] D-11 운영비 부담 체크 완료

광고(단계 2)는 공개 베타가 안정된 뒤에 켠다. 켜기 전에 Vercel 요금제 전환과 §11.1 규칙 준수를 다시 확인한다.

## 10. Claude 실행 프롬프트 추가 문단 (§14에 덧붙임)

> 위협 모델에서 가장 중요한 공격자는 같은 공간의 파트너다. 상대의 기기나 이메일을 손에 쥘 수 있고 압박할 수 있다고 가정해. 읽음 표시·접속 상태·정밀 완료 시각·위치를 만들지 마. 어떤 약속이든 한 사람이 혼자 즉시 철회할 수 있게 하고, 연결 해제에 장애물을 두지 마. 동의는 RPC로만 받고 화면이 본 내용 해시와 맞을 때만 기록해. 금전 약속 동의·정산 확정·내보내기·로그인 수단 변경은 단계 인증을 거쳐.
>
> Supabase에서는 `user_metadata`와 JWT 커스텀 클레임으로 권한을 판단하지 말고 매 요청 `memberships`를 확인해. 뷰는 `security_invoker`, 함수는 `search_path` 고정과 `public`·`anon` 실행 권한 회수, UPDATE 정책은 `WITH CHECK`와 열 단위 권한을 함께 써. 파트너에게 보일 열과 본인만 볼 열은 테이블을 나눠. 브라우저에서 DB로 직접 붙지 말고 서버를 거쳐.
>
> 성생활·피임·건강 주제는 저장 기능 없는 대화 카드로만 만들어. 소득은 저장하지 말고 비율은 5% 단위로 반올림해. 개인정보보호법(동의, 국외 이전, 파기, 만 14세 미만 차단)을 반영하고 서울 리전을 기본으로 해.
>
> 광고는 우리 도메인에서 내보내는 정적 배너만 쓰고, 외부 스크립트·iframe·픽셀·쿠키를 넣지 마. 로그인·설정 화면에만 두고, 사용자 데이터로 광고를 고르지 마. 노출·클릭은 사용자 식별 없이 하루 총합만 세. 후원은 외부 링크 하나뿐이고 후원 여부를 계정에 저장하지 마. §11.5 출시 관문을 통과하기 전에는 실제 사용자 데이터를 받지 마.
