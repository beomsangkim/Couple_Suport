# 함께 사는 두 사람을 위한 생활 합의 앱 — 제품·UI·보안 개발 명세

- 버전: 1.0
- 조사·작성 기준일: 2026-10-25
- 전달 대상: 제품 기획자, 디자이너, Claude 등 AI 코딩 에이전트, 개발자
- 문서 성격: 초기 조사와 이를 바탕으로 제안한 제품 요구사항. 실제 구현·보안 감사 완료를 의미하지 않는다.
- 우선순위: 개인정보·권한 보호 → 합의의 정확성 → 쉬운 사용 → 시각적 완성도 → 확장 기능.

> **제품 한 문장:** 함께 살기 시작한 두 사람이 생활비, 집안일, 일정, 생활 기준을 함께 정하고, 실행하고, 상황이 달라지면 다시 조정하는 앱.
>
> 성별, 성적 지향, 혼인 여부와 무관하게 사용할 수 있어야 한다. 특정 성별을 관리자·부양자·가사 담당으로 가정하지 않는다. 상대방을 감시하거나 기여도를 평가하는 서비스가 되어서는 안 된다.

## 1. 이 앱이 해결하는 문제

동거·신혼 초기에는 각자 익숙한 생활 방식이 하나의 공간에서 만난다. 돈을 반씩 내기로 해도 공동 지출의 범위가 다르고, 집안일을 나눠도 완료 기준이 다르며, 함께 산다는 이유로 개인 시간이나 정보까지 자동 공유되는 것으로 오해할 수 있다.

핵심 질문은 다음과 같다.

1. 무엇을 공동 책임으로 볼 것인가?
2. 돈·시간·관리 업무를 어떻게 나눌 것인가?
3. 누가 언제 어디까지 해야 완료인가?
4. 어떤 정보는 개인에게만 남겨둘 것인가?
5. 약속을 바꾸고 싶을 때 어떻게 제안하고 동의할 것인가?
6. 연결이 해제되면 접근 권한과 공동 기록은 어떻게 처리할 것인가?

### 1.1 조사에서 확인한 근거와 한계

- 커플 갈등 연구에서는 의사소통, 생활습관, 가사, 재정, 의사결정, 함께 보내는 시간, 성생활, 화면 사용, 역할 기대, 시간 관리 등이 갈등 주제로 보고됐다. [R1]
- 금전 갈등 연구는 돈 부족 외에도 비용 부담, 상대적 기여의 공정성, 소비에 대한 책임 인식을 다룬다. [R2]
- 국내 2024년 가사분담 지표에서는 공평하게 분담해야 한다는 견해가 68.9%였으나, 실제 공평하게 분담한다는 응답은 20%대였다. 신혼부부만의 통계가 아니다. [R3]
- 인지적 가사노동 연구는 직접 수행 외에 필요 예상, 선택지 탐색, 결정, 결과 확인을 별도 노동으로 설명한다. [R4]
- 동거 관련 전문기관 자료는 지출 범위, 계좌 운영, 가사, 장기 관계 기대를 미리 대화할 주제로 제시한다. 이는 한국 커플의 발생률 조사와 구분한다. [R5]

**아래 42개 항목은 위 연구와 생활 맥락을 종합한 기획용 분류다. 빈도 순위나 검증된 42문항 척도가 아니다. 사례 문장은 재구성했으며, 모든 커플에게 동일하게 적용되지 않는다.** 성소수자 커플의 갈등을 별도 결함이나 특수 문제로 취급하지 않는다.

## 3. 제품 범위와 기능 구조

### 3.1 핵심 사용 흐름

**문제 선택 → 각자 생각 정리 → 비교·대화 → 변경안 제안 → 두 사람 승인 → 일정·할 일·정산에 적용 → 재검토.**

예: 생활비를 60:40으로 나누기로 합의하면 적용 시작일을 저장하고, 다음 정산에 그 규칙을 사용한다. 이후 50:50 변경안을 제안하더라도 두 사람이 새 버전에 동의하기 전에는 기존 규칙이 유지된다.

| 캘린더 | 할 일·납부·재검토·공동 일정 통합 표시 | 외부 캘린더 동기화 |
| 개인 설정 | 표시 이름, 알림, 공유 범위, 세션, 연결 해제 | 기기별 보호 기능 |

초기 제외: 실제 송금·금융 계좌 연결, 위치 추적, 연락처 수집, 공개 커플 검색, 커플 순위, 애정 점수, AI의 갈등 판정, 건강·성생활 상세 추적, 파일 첨부, 민감정보 오프라인 동기화.

### 3.3 생활비 예시

공동생활비 200만 원, 월 소득 A 300만 원·B 200만 원인 가상 예시다.

| 방식 | A 부담 | B 부담 | 설명 |
|---|---:|---:|---|
| 반반 | 100만 원 | 100만 원 | 소득 대비 약 33.3%, 50% |
| 소득 비례 | 120만 원 | 80만 원 | 각자 소득의 40% |
| 직접 정하기 | 110만 원 | 90만 원 | 두 사람의 합의 반영 |

앱은 공정한 정답을 판정하지 않는다. 각 방식의 결과를 보여준다. 소득은 계산 중 기기 메모리에서만 처리하고, 저장 전에는 합의한 비율·금액만 보여준다. 화면 분석·오류 로그·URL에도 원소득을 넣지 않는다. 기기 내 계산 결과만 공유해도 비율로 소득 관계가 추정될 수 있다는 점은 필요한 맥락에서 안내한다.

### 3.4 약속과 일상 기록을 구분

- 약속: 분담 비율, 완료 기준, 공유 범위처럼 두 사람의 권리·책임을 바꾸는 규칙. 버전별 합의가 필요하다.
- 일상 기록: 장보기 지출, 청소 완료 등. 매번 두 사람 승인을 강요하지 않는다.
- 확정 정산: 두 사람이 같은 계산 결과를 확인한 기록. 앱은 실제 입금을 검증하지 않으므로 ‘송금 완료’와 ‘입금 확인’은 당사자의 수동 확인임을 명시한다.
- 수정 가능한 지출은 변경 내역을 남긴다. 확정된 정산에 포함된 지출은 조용히 덮어쓰지 않고 조정 기록으로 처리한다.

## 4. 쉬운 UI: 정보 구조와 화면 명세

아래 구성과 수치는 이 제품을 위한 제안이다. 토스의 공식 UI 규격을 복제한 것이 아니다.

### 4.1 모바일 우선 내비게이션

하단 탭은 **홈 / 생활비 / 일정 / 약속** 네 개를 우선한다. 집안일은 홈의 오늘 할 일과 일정의 필터로 접근한다. 설정은 프로필 영역에 둔다. ‘계산기·데이터베이스·워크플로’처럼 내부 도구 이름을 내비게이션에 노출하지 않는다.

| 화면 | 처음 보일 정보 | 주요 행동 | 접어둘 정보 |
|---|---|---|---|
| 홈 | 오늘 할 일, 이번 달 생활비 요약, 확인할 제안 | 맥락에 맞는 1개 주요 행동 | 지난 기록·통계 |
| 생활비 | 공동 지출, 나의 부담, 정산 상태 | 지출 기록하기 | 계산 상세·변경 이력 |
| 일정 | 오늘부터의 일정 목록 | 일정 추가하기 | 월간 격자·필터 |
| 약속 | 합의 중·적용 중·다시 볼 약속 | 약속 제안하기 | 이전 버전 |
| 설정 | 개인 보호·공유·계정 | 목적별 분리된 행동 | 개발자 정보 없음 |

홈에 거대한 소개 문구나 모든 기능 카드를 나열하지 않는다. 정보의 우선순위를 여백·제목·숫자로 구분하고, 모든 정보를 같은 크기의 카드에 넣지 않는다.

### 4.2 시작 과정

1. 계정 없이 가상 데이터로 예시 둘러보기. 실제 개인 데이터를 공개 체험에 저장하지 않는다.
2. 가입 후 표시 이름만 설정. 성별·성적 지향·혼인 상태·기념일·소득 입력은 요구하지 않는다.
3. ‘함께 사용할 사람 초대하기’ 또는 ‘먼저 둘러보기’를 선택한다.
4. 초대를 수락하기 전에 상대 표시 이름과 공유될 범위를 확인한다.
5. 첫 약속은 ‘생활비 나누기’ 또는 ‘집안일 나누기’ 중 하나만 시작한다.
6. 알림 허용은 필요한 기능을 사용한 맥락에서 요청한다. 거절해도 핵심 기능을 사용할 수 있다.

42개 주제를 가입 설문으로 한꺼번에 묻지 않는다. 기본 템플릿은 생활비·집안일·일정 세 가지이고, 민감 주제는 선택해서 연다.

### 4.3 약속 제안 화면

- 제목: ‘생활비를 어떻게 나눌까요?’
- 옵션: ‘반반 나누기 / 비율 정하기 / 금액 정하기’.
- 결과: 두 사람의 이름과 부담액을 동일한 위계로 표시한다.
- 부가 설정: 적용일, 다시 이야기할 날짜, 예외는 펼치기로 제공한다.
- 저장 전 요약: 공유 대상, 부담액, 적용 시작일을 명시한다.
- 버튼: ‘제안 보내기’. 아직 합의되지 않은 내용을 ‘저장 완료·적용 완료’로 표시하지 않는다.
- 수신 화면: 이전·새 조건의 차이, ‘동의하기 / 수정 제안하기 / 나중에 보기’.
- 제안에 응답하지 않았다는 이유로 비난 알림을 보내거나 자동 동의 처리하지 않는다.

### 4.4 지출 입력

필수 입력은 금액·내용·결제자. 날짜는 오늘, 분담 방식은 적용 중인 약속을 기본값으로 보여주되 수정할 수 있다. 기본값이 누가 얼마를 부담하게 하는지 숨기지 않는다.

한 화면에서 충분히 이해되는 짧은 입력을 불필요하게 여러 단계로 쪼개지 않는다. 복잡한 합의는 단계별로, 반복 기록은 짧은 폼으로 처리한다. 금액 입력에 숫자 키패드와 단위를 제공하고, 원본 입력값은 오류 후에도 보존한다.

### 4.5 집안일 상세

| 필드 | 예시 |
|---|---|
| 할 일 | 빨래 |
| 담당 | 민 |
| 반복 | 화요일·토요일 |
| 완료 기준 | 세탁·건조·개기·수납 |
| 함께 챙길 것 | 세제 부족 확인·구매 |
| 일정 변경 | 이번만 바꾸기 / 앞으로 바꾸기 |
| 교환 요청 | 상대 동의 전까지 기존 담당 유지 |

완료 버튼은 빠르게, 담당 변경은 분명하게 한다. 가사 건수로 기여 순위를 만들지 않는다. ‘많이 한 사람’ 대신 ‘조정이 필요한 일’을 찾도록 한다.

### 4.6 캘린더

- 기본은 오늘부터의 일정 목록. 월간 달력은 전환 옵션으로 둔다.
- 색만으로 사람을 구분하지 않고 이름·아이콘·텍스트를 함께 쓴다.
- 날짜 변경을 드래그만으로 제공하지 않는다. 편집 버튼과 키보드 조작을 지원한다.
- 일정 제목·상세·참석 정보를 어디까지 공유할지 알기 쉽게 표시한다.
- MVP에서 개인 캘린더 연동을 하지 않는다. 후속 연동 시 전체 공개 대신 사용자가 선택한 일정 또는 바쁨 여부만 공유하는 모드를 검토한다.

### 4.7 필수 화면 상태

| 상태 | 표시·행동 |
|---|---|
| 첫 사용·빈 목록 | 짧은 설명과 첫 행동 1개 |
| 로딩 | 레이아웃이 흔들리지 않는 로딩 표시 |
| 입력 오류 | 해당 입력 아래 원인과 수정 방법 |
| 통신 실패 | 입력 유지, 재시도, 저장 여부 명확히 표시 |
| 동시 수정 | 새 내용이 있음을 알리고 다시 확인 |
| 승인 대기 | 누구의 확인이 필요한지 중립적으로 표시 |
| 권한 소멸 | 내용을 제거하고 접근 종료 안내 |
| 완료 | 무엇이 저장·적용됐는지 설명 |

일반 할 일 완료는 실패 시 되돌릴 수 있는 즉시 반영을 검토할 수 있다. 합의 승인·정산 확정·연결 해제는 서버 확인 전에 성공으로 표시하지 않는다.

## 5. 토스 디자인 철학 조사와 적용

### 5.1 공식 자료에서 확인한 내용

토스의 공식 심플리시티 소개는 누구나 직관적으로 이해할 수 있는 디자인을 지향한다고 설명한다. [D1] 토스 UX 라이팅 자료는 명확함·간결함·친근함·존중·공감을 제시하며, 다음 행동을 예측하게 하는 문구, 불필요한 표현 제거, 쉬운 일상어, 강요하지 않는 표현 등을 다룬다. [D2]

**참고하는 것은 이해를 돕는 원칙이다. 토스의 브랜드·로고·화면·전용 컴포넌트를 복제하거나 공식 제휴를 암시하지 않는다.** 오래된 글은 발표 시점을 명시하며 토스의 모든 현재 내부 규칙이라고 단정하지 않는다.

### 5.2 이 제품에 대한 독자적인 적용 규칙

| 설계 규칙 | 적용 |
|---|---|
| 다음 결과를 예상할 수 있는 버튼 | ‘확인’ 대신 ‘제안 보내기’, ‘이 비율로 동의하기’ |
| 핵심 정보를 먼저 | 생활비 화면에서 부담액과 정산 상태를 먼저 |
| 필요한 시점에 상세 공개 | 적용일·예외·이력은 맥락에 맞게 펼침 |
| 사용자 언어 | ‘프로레이타’ 대신 ‘소득에 맞춰 나누기’ |
| 선택권 보장 | 초대·알림·템플릿은 나중에 설정 가능 |
| 비난 없는 상태 표현 | ‘또 안 했어요’ 대신 ‘일정을 조정할까요?’ |
| 정확한 성공 표현 | ‘제안을 보냈어요. 두 사람이 동의하면 적용돼요.’ |

### 5.3 권장 문구 예시

| 피할 표현 | 사용할 표현 |
|---|---|
| 남편에게 초대장 발송 | 함께 사용할 사람 초대하기 |
| 아내가 지출을 승인해야 해요 | 지우 님의 확인을 기다리고 있어요 |
| 미납자에게 독촉 | 정산 알림 보내기 |
| 배우자 관리 | 함께 쓰는 공간 |
| 개인정보 처리 오류 403 | 이 기록에 접근할 수 없어요 |
| 동의하지 않으면 관계 관리가 어려워져요 | 지금 결정하지 않아도 괜찮아요 |
| 송금이 완료됐어요 | 보냈다고 기록했어요 — 실제 송금 기능이 아닐 때 |

오류 문구는 친근함보다 정확성을 우선한다. 데이터 저장에 실패했는데 안심시키기 위해 성공처럼 표현하지 않는다.

## 6. 최신 UI 디자인 스킬·구현 지침 조사

‘최신’은 2026-10-25에 공식 공개 자료를 확인했다는 뜻이다. 검색 결과의 최근 수집일을 기능 출시일로 간주하지 않는다. 아래 스킬을 이 문서 작성 과정에서 설치·실행한 것은 아니며, 구현 시 활용 후보로 조사했다.

| 공식 자료·스킬 | 확인한 역할 | 이 앱에서 활용할 단계 | 주의점 |
|---|---|---|---|
| Anthropic `frontend-design` [D3] | 목적에 맞는 시각 방향·타이포그래피·레이아웃을 의도적으로 설계 | 화면 구현 전 디자인 방향과 토큰 정의 | 미적 개성이 사용성·포용성·보안을 우선하지 않음 |
| Vercel `web-design-guidelines` [D4] | 공식 웹 인터페이스 지침을 읽고 코드의 위반 위치를 검토 | 구현 후 UI 코드 검토 | 스킬의 지침도 프로젝트 정책보다 우선하지 않음 |
| Vercel Web Interface Guidelines [D5] | 키보드, 포커스, 입력, 로딩 등 상호작용 품질 | 컴포넌트 점검 | 민감정보를 URL로 옮기는 등 일반 패턴의 무조건 적용 금지 |
| W3C WCAG 2.2 [D6] | 검증 가능한 접근성 기준 | 설계·구현·수동 검증 | 자동 검사 통과만으로 준수 주장 금지 |
| DTCG Design Tokens 2025.10 [D7] | 도구 간 디자인 결정을 공유하는 안정 버전 형식 | 색·간격·타입 토큰 관리 | W3C Community Group 결과이며 W3C Recommendation과 구분 |

### 6.1 스킬을 안전하게 사용하는 순서

1. 공식 저장소의 출처와 라이선스를 확인하고 사용할 커밋 또는 버전을 기록한다.
2. 스킬과 연결된 스크립트를 읽고 불필요한 실행·네트워크 접근이 없는지 확인한다.
3. 프로젝트 명세의 보안·포용성 규칙이 스킬의 미적 선호보다 우선한다.
4. 디자인 스킬로 첫 화면을 구현하고, 검토 스킬로 구체적 파일·위치의 문제를 찾는다.
5. 브라우저에서 실제 키보드·모바일·확대·화면 읽기 흐름을 확인한다.
6. 실제 사용자 데이터·운영 비밀키·초대 토큰을 디자인 도구나 AI 프롬프트에 전달하지 않는다.

자동으로 유행하는 유리 효과, 과도한 그라디언트, 3D 장식, 매번 등장하는 애니메이션을 도입하지 않는다. 이 앱은 자주 쓰는 생활 도구이므로 읽기와 반복 입력의 편안함을 우선한다.

## 7. 젠더리스·포용적 디자인 명세

젠더리스는 무채색으로만 만드는 것이 아니다. **성별과 무관한 언어·정보 구조·역할·권한·개인정보 보호**를 일관되게 구현하는 것이다. 아래는 이 제품의 설계 제안이다.

### 7.1 가입·모델·권한

- 성별, 성적 지향, 법적 혼인 상태를 수집하지 않는다. 기능에 필요하지 않다.
- `husband`, `wife`, `male_owner`, `female_partner` 필드를 만들지 않는다.
- 내부 모델은 `user`, `household`, `membership`, `participant` 등으로 구성한다.
- 사용자 노출은 표시 이름을 우선하고 필요하면 ‘나’, ‘함께하는 사람’, ‘파트너’를 쓴다.
- 표시 이름은 법적 이름과 분리한다. 동일한 표시 이름도 허용하고 내부 ID로 구분한다.
- 초대한 사람이 상대의 계정을 관리하거나 더 넓은 정보 열람권을 갖지 않는다.
- 두 명이 쓰는 MVP라는 범위 제한은 성별·혼인 형태 제한과 구분한다.
- 성별이나 소득을 근거로 가사·재정 역할을 추천하지 않는다.

### 7.2 시각 요소

- 남성=파랑, 여성=분홍 같은 자동 배정을 하지 않는다. 두 사람에게 동등한 색 선택권을 준다.
- 기본 아바타는 이니셜·도형. 외모·사진에서 성별을 추론하지 않는다.
- 기본 일러스트는 공동생활의 물건과 행동 중심. 인물을 쓸 경우 다양한 표현을 자연스럽게 포함한다.
- 결혼·출산·이성 커플을 서비스의 기본 성공 경로로 시각화하지 않는다.
- 무지개 테마를 특정 사용자에게 자동 적용하거나 성적 지향을 추측하지 않는다.
- 두 사람의 이름·금액·아바타 크기는 같은 위계로 표시한다.

### 7.3 관계 정보 보호

- 공개 프로필, 연락처 기반 사용자 추천, 검색 가능한 커플 목록을 만들지 않는다.
- 푸시·이메일 제목에 상대 이름, 커플 관계, 소득, 약속 내용을 기본 포함하지 않는다.
- 푸시 미리보기 기본값은 ‘확인할 항목이 있어요’. 세부 노출은 본인이 선택한다.
- 앱 이름·아이콘 자체가 사용 사실을 드러낼 수 있다. 앱 설치 사실까지 감출 수 있다고 보장하지 않는다.
- 초대 링크 미리보기와 OG 메타데이터에는 관계·이름·본문을 넣지 않는다.
- 관계 공개 범위는 사용자가 결정한다. 가족·혼인 공개를 요구하지 않는다.
- 연결 해제를 위해 상대 동의를 강요하지 않는다. 계정 삭제와 연결 해제는 별도 행동이다.

### 7.4 검수 시나리오

동성 커플, 이성 커플, 논바이너리 사용자가 포함된 커플, 비혼 동거, 법적 이름과 표시 이름이 다른 사용자, 가족에게 관계를 공개하지 않은 사용자 모두가 별도 우회 없이 가입·합의·정산·탈퇴할 수 있어야 한다. 정체성을 공개하도록 요구하지 않고 가상 시나리오로도 검수한다.

## 8. 제안하는 시각 디자인 시스템

다음 값은 출발점이다. 실제 조합·상태별 대비와 가독성을 검증한 뒤 확정한다. 특정 색 자체를 젠더리스라고 규정하지 않는다.

| 토큰 | 초안 | 용도 |
|---|---|---|
| `background` | `#F7F8FA` | 기본 배경 |
| `surface` | `#FFFFFF` | 입력·내용 영역 |
| `text-primary` | `#20252B` | 제목·본문 |
| `text-secondary` | `#525D69` | 보조 설명 |
| `accent` | `#006B65` | 주요 버튼·선택 상태 |
| `danger` | `#B42318` | 오류·파괴적 행동 |

- 방향: 차분하고 실용적인 생활 도구. 과도하게 로맨틱하거나 금융 대시보드처럼 차갑게 만들지 않는다.
- 폰트: 한국어 가독성이 좋은 시스템 폰트 스택 또는 라이선스를 확인한 자체 호스팅 폰트. 숫자는 금액 열에서 폭을 맞춘다.
- 본문 기본 16px, 보조 정보 14px부터 검토. 핵심 정보를 작은 글자로 숨기지 않는다.
- 간격은 4/8/12/16/24/32px 등 제한된 토큰으로 관리한다.
- 버튼 높이 48px를 제품 기준으로 제안한다. 모바일 터치 영역은 최소 44×44 CSS px를 목표로 한다.
- 본문은 좌측 정렬, 금액은 목록에서 비교가 쉬운 정렬. 버튼명은 짧고 구체적이다.
- 모션은 결과 이해를 돕는 짧은 전환 위주. `prefers-reduced-motion`을 따른다.
- 라이트 모드를 우선 완성한다. 다크 모드는 별도 토큰과 대비 검증 후 제공한다.
- 반응형은 최소 320 CSS px 폭에서 본문 가로 스크롤 없이 사용 가능하게 한다. 큰 표는 카드형 또는 열 선택으로 바꾼다.
- 데스크톱에서는 모바일 화면을 과도하게 늘이지 않고 콘텐츠 폭과 탐색 구조를 조정한다.

### 8.1 접근성 기준

WCAG 2.2 AA를 목표로 한다. 일반 텍스트 대비 4.5:1, 큰 텍스트 3:1, 필요한 UI 경계·상태 대비 3:1을 검증한다. WCAG AA의 타깃 크기 최소 기준은 예외를 포함해 24×24 CSS px이며, 이 제품의 44px 목표는 더 큰 자체 기준이다. [D6]

키보드 사용, 가려지지 않는 포커스, 적절한 레이블, 오류 연결, 상태 알림, 드래그 대체, 200% 텍스트 확대, 확대를 막지 않는 화면을 확인한다. 인증에서 비밀번호 관리자·붙여넣기를 허용하고 기억·퍼즐에만 의존하지 않는다. 달력의 격자 조작이 어렵다면 동등한 목록·날짜 입력 경로를 제공한다.

## 10. 보안 요구사항

### 10.1 위협 모델

| 주체·상황 | 보호할 것 |
|---|---|
| 비로그인 사용자 | 계정·공간·초대 정보 열거 방지 |
| 다른 공간의 로그인 사용자 | ID 변경·직접 API 호출에 의한 접근 방지 |
| 현재 파트너 | 개인 정보 열람·상대 승인 위조·계정 지배 방지 |
| 연결 해제된 파트너 | 기존 세션·캐시·구독을 통한 향후 접근 방지 |
| 탈취된 계정·기기 | 세션 회수·재인증·다중 인증·최소 정보 노출 |
| 서버·운영 계정 침해 | 최소 권한·암호화·키 분리·감사·수집 최소화 |
| 공급망·AI 도구 | 비밀키·실데이터 유출과 악성 의존성 방지 |

### 10.2 인증·세션

- 직접 비밀번호 시스템을 만들지 않고 관리형 인증을 사용한다.
- 이메일 검증, 안전한 복구, 로그인·재설정 요청 제한, 토큰 만료·회수를 구현한다.
- 운영 계정은 MFA 필수. 사용자에게도 지원하며 민감 작업의 재인증 정책을 정한다.
- 웹 MVP는 서버 중심 세션을 우선 검토한다. 쿠키는 실제 인증 구조에 맞게 Secure·HttpOnly·SameSite와 CSRF 방어를 설계한다. 브라우저 SDK가 토큰을 읽는 구조와 무조건 HttpOnly를 혼합하지 않는다.
- 모든 기기 로그아웃, 계정 변경, 만료 상태를 검증한다. 토큰을 URL·분석 이벤트·로그에 남기지 않는다.

### 10.3 인가·DB 격리

로그인 여부와 개별 데이터 접근 권한은 별도다. 모든 서버 함수·API에서 현재 사용자와 대상 기록에 대한 권한을 확인한다. Next.js의 페이지·미들웨어 검사만으로 충분하다고 가정하지 않는다. [S1][S2]

- 기본 거부, 최소 권한, 요청마다 검사한다. [S3]
- 공동 데이터에는 `household_id`, 개인 데이터에는 소유자를 명시한다.
- 읽기·생성·수정·삭제를 분리해 RLS와 DB 권한을 설계한다.
- 클라이언트의 `user_id`, `approved_by`, `household_id`는 권한 증명이 아니다. 승인자는 검증된 세션에서 정한다.
- 행의 소속·소유자 변경, 임의 멤버십 생성, 자기 권한 상승을 막는다.
- 일반 요청은 사용자 권한이 적용되는 DB 경로를 사용한다. 관리자 secret/service-role 키는 RLS를 우회하므로 브라우저 노출 및 일반 요청의 포괄적 사용을 금지한다. [S4]
- publishable 키 자체가 비밀인 것은 아니다. 키를 숨기는 대신 실제 정책을 검증한다.
- RLS 정책 오류를 해결하기 위해 RLS를 끄지 않는다. 함수·뷰·관리자 역할의 우회 경로도 검토한다.
- 서비스용 고권한 함수는 최소 권한, 고정된 탐색 경로, 실행 권한 제한, 입력 검사를 갖추고 필요한 경우에만 사용한다.

### 10.4 초대·연결 해제

- 초대는 충분히 예측 불가능한 토큰, 짧은 유효기간, 일회 사용, 취소 기능을 가진다. 서버에는 토큰 해시를 저장한다.
- 링크를 열기만 해서는 가입되지 않는다. 로그인·검증된 수신 대상 확인·명시적 수락을 거친다. 개인정보를 공개하지 않는 초대자 확인 절차도 둔다.
- 링크 토큰이 로그·분석·Referer에 유출되지 않도록 한다. 초대 화면에 제3자 추적 코드를 넣지 않는다.
- 동시 수락에도 정원을 넘지 않도록 DB 트랜잭션과 잠금·제약으로 처리한다.
- MVP 권장 정책: 연결 해제 시 공동 공간을 종료 상태로 만들고 일반 공유 접근을 차단한다. 각자 계정은 유지한다. 보존·내보내기·삭제 범위는 별도 명시적 정책으로 정하고, 새 파트너에게 이전 기록을 승계하지 않는다.
- 연결 해제는 상대방 허락 없이 가능하다. 종료 전 본인이 볼 수 있는 자료만 내보낼 수 있으며 상대의 비공개 정보는 포함하지 않는다.
- 연결 해제 이후 백그라운드 작업·알림·실시간 구독도 권한을 재검사한다.
- 이미 본 화면·스크린샷·다운로드를 회수할 수 있다고 약속하지 않는다.

### 10.5 데이터 최소화·암호화

- 주민번호·성적 지향·건강·정확한 위치·연락처·금융 인증정보를 수집하지 않는다.
- HTTPS/TLS, 저장 데이터·백업 암호화, 운영 키 관리와 회전을 검증한다.
- 전송·저장 암호화는 운영자도 읽을 수 없는 E2EE와 다르다.
- 초기 기본안은 엄격한 접근 통제와 수집 최소화. ‘운영자도 본문을 읽지 못함’이 필수라면 구현 전 E2EE를 별도 아키텍처 결정으로 확정한다.
- E2EE 도입 시 다중 기기·복구·파트너 키 교체·연결 해제·검색·알림·정산 처리의 제약을 제시한다. 자체 암호 알고리즘을 만들지 않는다.
- 민감정보를 저장하지 않는 것이 우선 방어다. [S5]

### 10.6 입력·브라우저·캐시

- 서버에서 금액 범위·문자 길이·허용 필드·식별자·시간을 검증하고 허용 목록 기반으로 저장한다.
- 매개변수화된 쿼리를 사용한다. 사용자 입력을 SQL·HTML에 직접 삽입하지 않는다.
- MVP의 약속 본문은 평문으로 처리한다. HTML 렌더링이 필요하면 별도 검증된 정화 정책이 필요하다.
- CSP와 적절한 보안 헤더, 인증 방식에 맞는 CSRF·Origin 검증을 설정한다. CORS만으로 인가를 대신하지 않는다.
- 인증·초대·내보내기·비용 큰 작업에 요청 제한을 둔다.
- 인증 응답을 공용 CDN·공유 서버 캐시에 저장하지 않는다. 사용자 A의 응답이 B에게 재사용되지 않는 테스트를 둔다.
- MVP에서 민감 데이터를 localStorage·서비스 워커·IndexedDB에 영구 저장하지 않는다. 로그아웃·권한 소멸 시 앱 메모리·클라이언트 쿼리 캐시를 비운다.

### 10.7 운영·개발 도구

- 개발·테스트·운영 환경과 키를 분리하고 개발에는 가상 데이터만 사용한다.
- 비밀정보를 Git·브라우저 번들·AI 대화에 넣지 않는다. 유출 시 파일에서 지우는 것과 별개로 키를 폐기·회전한다.
- 에러 추적·분석에서 본문·금액·이름·이메일·토큰을 마스킹한다. 민감 화면의 세션 리플레이는 끈다.
- 감사 이벤트는 행동자·대상·행동·결과·시간 중심으로 최소화한다. 민감한 원문 복사본을 감사 로그에 쌓지 않는다.
- 운영자의 사용자 데이터 접근은 필요 시 제한·기록하고 광범위한 기본 열람을 피한다.
- 의존성·비밀정보·정적 분석 검사를 CI에 넣는다. 발견 결과를 실제 수정·검증한다.
- 백업의 보존·삭제·복원 절차와 복원 시 이미 삭제된 데이터의 재등장 방지 정책을 문서화한다.
- 출시 전 실제 운영 설정·메일·배포·복구까지 포함해 별도 보안 검토를 수행한다.
- OWASP ASVS 5.0의 적용 가능한 Level 2 요구사항을 목표로 추적표를 만든다. 미검증을 통과로 표시하지 않는다. [S6]

## 11. 데이터 모델과 상태 규칙

### 11.1 최소 엔터티

| `invitations` | 토큰 해시·만료·수신 대상·사용·취소 상태 |
| `agreements` | 공간·주제·현재 적용 버전 |
| `agreement_versions` | 내용·적용일·상태·생성자. 승인 이후 불변 |
| `approvals` | 버전·승인 사용자·시각. 사용자별 유일성 |

‘공동 테이블에 숨김 플래그만 두고 모든 데이터를 브라우저에 내려보내기’는 금지한다. 개인 초안 기능을 추가하면 소유자 전용 저장·정책부터 설계한다.

### 11.2 합의 상태

`개인 초안 → 제안됨 → 두 사람 승인 → 적용 대기 또는 적용 중 → 새 합의로 대체 / 종료`

- 제안자가 전송할 때 자신의 동의를 함께 기록할지는 UI에 명시한다.
- 내용이 바뀌면 새 버전이며 기존 승인은 재사용하지 않는다.
- 상대가 수정안을 보냈다면 새 버전에 두 사람의 동의가 필요하다.
- 두 명의 활성 구성원과 같은 버전에 대한 동의를 서버·DB가 확인한다.
- 향후 적용일이면 기존 규칙을 적용일까지 유지한다.
- 감사 기록과 제품 이력은 개인정보 보존·삭제 정책의 예외로 무한 보관하지 않는다.

### 11.3 계산·동시성

- 원화는 정수 단위, 다중 통화 확장 시 통화의 최소 단위를 사용한다. 부동소수점 오차를 피한다.
- 10,001원 반반 분담처럼 나머지가 생기면 누가 1원을 부담하는지 결정적이고 보이는 규칙을 둔다.
- 합계는 원 지출과 같아야 한다. 음수·환불·수정은 별도 정책으로 처리한다.
- 지출 기록과 정산 확정에 idempotency key 또는 동등한 중복 방지를 적용한다.
- 버전 번호·갱신 조건으로 오래된 화면의 덮어쓰기를 막는다.
- 과거 정산에는 당시 배분을 보존한다. 현재 약속 변경이 과거 확정액을 바꾸지 않는다.
- 종일 일정은 날짜로, 시각 일정은 시간대와 함께 처리한다. 반복 생성은 시간대·월말·예외를 테스트한다.

### 12.1 보안 필수 시나리오

별도 공간 A의 두 사용자, 공간 B의 두 사용자, 비로그인 사용자, 탈퇴 사용자로 테스트한다. 권한 없는 요청이 막히는 것뿐 아니라 정상 사용자 요청이 성공하는 것도 확인한다.

|---|---|---|

### 12.2 기능·UI 검증

- 분담 합계·나머지·환불·과거 규칙 보존 테스트.
- 합의 상태 전환·날짜 적용·재검토·작업 생성 테스트.
- 빈 화면·통신 실패·충돌·접근 종료 상태를 실제 화면에서 확인.
- 320/390/768/1280px 등의 화면과 큰 글씨에서 레이아웃 확인.
- 키보드만으로 가입·초대·제안·정산을 완료할 수 있는지 확인.
- 스크린리더 레이블·상태 전달·포커스 복귀를 수동 확인.
- 색상 없이 상태·담당자를 식별할 수 있는지 확인.
- 동일 표시 이름·긴 이름·한글·다른 문자 이름으로 UI와 데이터 소유권을 확인.

### 12.3 사용성 평가 목표 — 조사 결과가 아닌 초기 제품 목표

가상 데이터로 소규모 참여자 테스트를 수행한다. 성적 지향 공개는 요구하지 않고 다양한 관계 시나리오를 포함한다.

| 과제 | 목표 |
|---|---|
| 홈에서 오늘 할 일 찾기 | 설명 없이 위치를 이해 |
| 30,000원 지출 기록 | 도움 없이 약 30초 내 완료를 목표로 측정 |
| 생활비 변경 제안 | 제안과 적용의 차이를 설명할 수 있음 |
| 공개 범위 확인 | 누가 볼 수 있는지 정확히 답함 |
| 연결 해제 찾기 | 도움 없이 찾고 결과를 이해 |

5~8명 수준의 초기 테스트는 문제 발견용이지 전체 시장의 성공률 추정용이 아니다. 관찰 결과에 따라 목표와 화면을 수정한다.

## 13. 구현 순서와 납품물

1. **설계:** 위협 모델, 데이터 흐름, 권한표, DB 구조, 연결 해제·암호화 결정 기록.
2. **핵심 기반:** 인증·공간·초대·RLS. 정상·비정상 접근 테스트부터 완료.
3. **약속 기능:** 버전·승인·적용일과 UI 상태 구현.
4. **생활비:** 계산·지출·정산 스냅샷·중복 방지 구현.
5. **생활 관리:** 할 일·반복·캘린더·알림 구현.
6. **UI 검토:** 공식 디자인 스킬·지침을 참고해 화면과 접근성 검토.
7. **출시 검증:** 운영 키·로그·복구·삭제·보존·배포 설정과 별도 보안 검토.

필수 납품물: 실행 코드, 마이그레이션·RLS 정책, 권한표, 테스트·실행 결과, 디자인 토큰·컴포넌트 상태, 운영·복원 안내, 미해결 위험 목록. 앱 화면에 이 개발 문서를 그대로 노출하지 않는다.

구현 전 결정이 필요한 사항: E2EE 필수 여부, 연결 종료 기록의 보존 기간·접근 방식, 인증 제공자와 세션 구조, 배포 지역·운영 로그 보존. 이 문서의 기본안으로 가능한 작업은 진행하되 미정 사항을 안전하다고 임의 선언하지 않는다.

## 14. Claude에게 전달할 실행 프롬프트

> 이 문서 전체를 제품 명세로 사용해 함께 사는 두 사람의 생활 합의 앱을 구현해줘. 문서 앞의 42개 항목은 해결할 문제의 지도이며, 모든 주제를 가입 설문이나 필수 데이터로 수집하지 마.
>
> 초기 기능은 버전별 합의, 생활비 분담 계산과 수동 정산, 반복 집안일, 공유 캘린더야. 먼저 위협 모델·권한표·DB 구조·핵심 화면 구조를 제시하고, 인증·공간 격리·초대의 테스트부터 구현해.
>
> 일반 데이터 요청에서 관리자 키로 RLS를 우회하지 마. 모든 API·서버 함수·DB 정책이 사용자의 현재 권한을 확인하도록 해. 상대 승인 위조, 공간 ID 변경, 개인 데이터 노출, 연결 해제 후 접근, 캐시 혼합을 테스트해. 테스트를 통과시키기 위해 보안 규칙을 끄거나 완화하지 마.
>
> UI는 쉬운 생활 언어와 명확한 다음 행동을 우선해. 토스 공식 자료의 명확함·간결함·존중을 참고하되 브랜드와 화면을 복제하지 마. 공식 frontend-design과 web-design-guidelines를 활용할 경우 출처·버전을 확인하고 이 문서의 보안·접근성·포용성 요구를 우선해.
>
> 성별·성적 지향·혼인 여부를 요구하지 마. 표시 이름·중립적 아바타·동등한 권한을 사용하고, 초대한 사람에게 상대 계정의 관리 권한을 주지 마. 성별 색상·남편과 아내의 고정 역할·결혼과 출산의 강제 경로를 만들지 마. 알림과 초대 미리보기에 관계 정보를 노출하지 마.
>
> 홈·생활비·일정·약속 네 개의 핵심 탐색을 구현하고, 정상 화면뿐 아니라 빈 상태·로딩·실패·충돌·접근 종료까지 완성해. WCAG 2.2 AA를 목표로 자동 검사와 수동 검증을 병행해.
>
> 계산은 최소 화폐 단위로 정확히 처리하고, 과거 정산에는 당시 규칙을 보존해. 승인된 약속 변경은 새 버전으로 처리해. 두 사람이 같은 버전에 동의해야 적용되게 해.
>
> 개발에는 가상 데이터만 사용해. 비밀키·개인정보를 AI 입력·로그·Git에 넣지 마. E2EE를 구현하지 않았다면 운영자도 읽을 수 없다고 표현하지 마. 완료 보고에는 실제 실행한 검증과 미검증·미해결 항목을 구분해서 적어줘.
